01SYSTEM ARCHITECTURE

four layers · strict separation · one authority per concern

The Guardian–Nexus system is built from four distinct layers. Each layer has exactly one job and does not bleed into another's responsibility. Violating these boundaries is the primary cause of routing chaos in systems like this.

GUARDIANCDP execution engine + DOM observer. The only system that touches the browser.
↓ emits Callto objects ↓
IR RESOLVERIntent classification + routing. The only system that decides where a Callto goes.
↓ routes to ↓
NEXUSMemory + orchestration + policy. The only system that retains meaning over time.
also inside Guardian ↓
LISTENERPersistent DOM observer (Guardian subsystem). Continuous event generator only. No routing or decision authority.
◈
THREE AUTHORITY LAWS
Guardian is the only system that touches the browser.
IR Resolver is the only system that decides where a Callto goes.
Nexus is the only system that retains meaning over time.

SYSTEM FLOWS

PRIMARY INGESTION (observation)
DOM event
→ Guardian (CDP capture)
→ Callto object
→ IR Resolver (classify intent + select route)
→ Nexus (store + contextualize)
EXECUTION FLOW (command)
Nexus instruction
→ IR Resolver (build ExecutionPlan)
→ Guardian (CDP execution)
→ Callto result
→ Nexus (update state)
LISTENER FLOW (reactive)
DOM mutation
→ Guardian Listener subsystem
→ Callto (type: "mutation" | "listen")
→ IR Resolver (optional reroute)
→ Nexus (state update or trigger workflow)

NO-OVERLAP RULES

  • Guardian must never decide routing targets
  • Nexus must never execute CDP operations
  • IR Resolver must never persist long-term state as authority — transient decisions only
  • Listener must never route, interpret, or make decisions — only emit Callto events
  • No direct module-to-module communication — all execution routes through the event bus

05CALLTO OBJECT

immutable event snapshot · atomic system record · no routing logic inside

A Callto is the atomic record of an interaction, observation, or instruction. Immutable after creation. Contains no routing logic — routing is fully externalized to the IR Resolver.

SCHEMA

{
  id:          "callto-a1b2c3d4",
  source:      "guardian",
  instanceId:  "guardian-3000b1c2-0669-4d5a-a9b4-3f1e06cc4420", // opaque string — format: guardian-{uuid}
  type:        "capture|execute|listen|mutation|error",
  intent:      "click|type|extract|observe|stream|system",
  selector:    "css-selector",
  xpath:       "//path/to/element",
  url:         "https://...",
  host:        "example.com",
  payload:     {},
  fingerprint: { rect: {top,left,width,height}, text: "..." },
  state:       "created|executed|failed|observed",
  timestamp:   1713312000000,
  route:       { type: "nexus" },            // RouteSpec — assigned by IR Resolver
  routeTrace:  [],                           // populated as packet moves through IR
  routeHint:   {}                            // optional hint from Guardian to IR
}

PROPERTIES

  • Immutable after creation
  • Traceable to DOM origin or execution trigger
  • Contains no routing logic — all routing externalized to IR Resolver
  • Every Callto includes instanceId (format: guardian-{uuid}, e.g. guardian-3000b1c2-0669-…) so Nexus identifies the source Guardian session
  • Failed Calltos enter IR Layer retry queue: backoff 1s → 5s → 15s → 60s, max 4 attempts

06IR RESOLVER

intent-routing layer · the only system that decides where a callto goes

The IR Resolver (ir-layer.js) converts Callto objects into executable routing plans. It is the single routing authority. No Callto reaches any destination without passing through it.

RESPONSIBILITIES

  • Intent classification (click, stream, extract, system action, etc.)
  • Target resolution (Guardian-local, Nexus, storage, external node)
  • Route selection and execution (nexus, local, mesh, pipeline, conditional)
  • Fallback planning when primary routes fail
  • Confidence scoring for ambiguous inputs
  • Mutation-aware rerouting when selector becomes invalid
  • Retry queue management with exponential backoff

EXECUTIONPLAN SCHEMA

{
  calltoId:      "callto-a1b2c3d4",
  target:        "guardian | nexus | local | mesh",
  action:        "click | type | extract | observe | stream",
  endpoint:      "url | nodeId | tabId",
  mode:          "sync | async | stream",
  confidence:    0.95,
  fallbackChain: [],
  requiresAck:   true
}

ROUTE TYPES

ROUTEWHAT IT DOESBEST FOR
nexusPOST to Nexus /ingest. Expects full ACK. Retries on failure.Default production route
localSaves to browser.storage.local. Persistent. Max 500 entries.Offline work, backup
meshBroadcast via Nexus node registry to all registered instances. Not peer-to-peer — all routing is registry-mediated.Multi-instance fan-out
analyzeURCK kernel only. Zero outbound network.Auditing without sending
pipelineSequential multi-step execution. Steps share the same Callto packet.Redundancy, sequential workflows
conditionalRule-based: evaluates host, selector, intent, confidence. First match wins.Domain-aware routing

NEXUS INGEST ACK — REQUIRED RESPONSE

{
  ok:        true,
  calltoId:  "callto-a1b2c3d4",
  received:  true,
  stored:    true,
  indexed:   true,
  tier:      "hot",
  serverTs:  1713312000000,
  routePath: ["guardian","nexus"]
}

If Nexus does not return this schema, IR Resolver treats the ingest as failed and retries. No silent acceptance.

i
CONDITIONAL ROUTING DEFAULTS
Built-in rules: claude.ai traffic routes to Nexus; fingerprint confidence below 0.6 routes to local storage. This prevents low-confidence captures from polluting the Nexus index.

08LISTENER SUBSYSTEM

guardian subsystem · persistent dom observer · continuous event generator only

The Listener is a Guardian subsystem, not a separate layer. It is a persistent observation mode — Guardian running a standing CDP query. It does not decide what mutations mean. It only emits Callto events when DOM changes occur. Meaning is assigned by the IR Resolver.

◈
WHAT LISTENER IS AND IS NOT
Listener IS: a continuous Callto event generator. That is its entire job.
Listener is NOT: a routing system, a workflow engine, a state tracker, or a decision system.
Listeners produce signals. IR Resolver decides what those signals become.

CREATING A LISTENER — SEPARATE PATH

Listeners are created through a completely separate path from Calltos. After picking an element, click ⦿ LISTEN in the callto popup. A separate purple-themed Listener Config Modal opens. This modal has its own DOM element, its own fields, and its own confirm button. It does not share state with the callto popup.

⦿ LISTENER CONFIG MODAL
Element
Read-only. The selector of the element you picked. Re-pick to change.
Label
Optional human-readable name shown in the LISTEN tab.
Observe Mode
DOM mutations — all child/text changes via MutationObserver.
Input / value changes — input + change events on form fields.
Chat messages (AI) — MutationObserver tuned for AI chat stream containers.
Emit Callto Type
mutation or listen — the type field set on emitted Calltos.
Link Target
Optional routing override for mutation Calltos. Options: Another Bridge / Guardian, Trigger a Callto (by ID), External Endpoint (HTTP URL), or Nexus via IR Layer. If unset, IR Resolver default applies.

Click ⦿ START LISTENER. The listener attaches to the element. A purple badge appears on it. The LISTEN tab in the popup shows it as ACTIVE.

11PULSE SYSTEM

ir layer heartbeat · 1.5s interval · presence registry update

Guardian's IR Resolver emits a pulse packet to Nexus every 1.5 seconds. This is the presence and node discovery mechanism for the entire mesh. The instanceId format is guardian-{uuid} — an opaque string where the prefix is separated by a hyphen, e.g. guardian-3000b1c2-0669-4d5a-a9b4-3f1e06cc4420. The opaque token prevents collision between instances. A display short ID is derived from the first 8 chars of the UUID segment for UI purposes — never used for routing.

PULSE PACKET

{
  type:         "guardian:pulse",
  logicalId:    "guardian",
  instanceId:   "guardian-3000b1c2-0669-4d5a-a9b4-3f1e06cc4420",
  ts:           1713312000000,
  port:         3747,  nexusPort: 3748,
  capabilities: ["capture","callto:emit","listener","route","ir"],
  intents:      ["nexus","local","broadcast","pipeline","analyze"],
  version:      "3.0.0"
}

12NEXUS SERVICE

memory + orchestration + policy · the only system that retains meaning over time

Nexus is the system brain. It does not interact with the DOM. It manages meaning, history, and system-wide coordination. It receives Callto objects from the IR Resolver and stores, contextualizes, and orchestrates workflows from them.

◈
NEXUS DOES NOT
Touch the DOM · Execute CDP commands · Resolve selectors · Interpret raw browser events without the IR Resolver

RESPONSIBILITIES

  • Persistent storage of Callto history (HOT → WARM → COLD tiers)
  • Workflow orchestration across multiple Calltos and sessions
  • Policy enforcement — routing rules and constraints fed to IR Resolver
  • Cross-session context aggregation and memory enrichment
  • Multi-step task decomposition
  • System-wide state tracking
  • Coordination of multiple Guardian instances

CAUSAL EDGES

When a callto executes and a result arrives, URCK links command:running to command:success or command:failed via a causal/adapter edge. Every result is traceable back to the original capture in the event graph.

15TROUBLESHOOTING

common issues · architecture violations · diagnostic procedures

ARCHITECTURE VIOLATION CHECKLIST — CHECK THESE FIRST
  • Is Guardian deciding routing targets? → It must not
  • Is Nexus executing CDP commands? → It must not
  • Is the IR Resolver persisting long-term state as authority? → It must not
  • Is a Listener routing, interpreting, or making decisions? → It must not
  • Is any module communicating directly with another without the event bus? → It must not
Extension won't install
Use about:debugging → Load Temporary Add-on → manifest.json. Never drag the zip to about:addons.
NEXUS pill stays red
Start Nexus on port 3748. Ensure POST /pulse and GET /health are registered. Run Nexus Service diagnostic. Check URL in Settings.
Calltos not reaching Nexus
Check route selector — must include Nexus. Run IR Layer diagnostic. If retry queue is climbing, Nexus is not returning the required ACK schema. Verify /ingest returns { ok, received, stored, indexed }.
Retry queue growing
Nexus not responding or returning errors on /ingest. Check Nexus logs. Switch to Nexus + Local backup route so data is preserved while debugging.
LISTEN opens wrong thing
In v3, LISTEN opens a separate purple Listener Config Modal. If you see the callto popup's link screen instead, you are on v2. Update to v3.
Listener not attaching
Element not found by selector or XPath at attach time. Check the LISTEN tab for error events with type: "error", reason: "Element not found". Use a more stable selector — prefer id attributes.
No nodes in Devices tab
Click SCAN. Ensure Nexus is running and receiving pulses. Discovered nodes come from the pulse registry. Add manually if you know the IP/port.
Bridge pill stays red
Start bridge-node.js on port 3747. Run Bridge Connection diagnostic for the exact error message.
IR Layer test fails
Check about:debugging → Guardian → Inspect for background script errors. Most common cause: ir-layer.js not loading before background.js. Verify manifest order: ["urck.js", "ir-layer.js", "background.js"].
Instance not found in registry
Both Guardian instances must be connected to the same Nexus for BY INSTANCE ID to work. The target must have pulsed within the last 30 seconds. If it's not in the registry, use BY IP + PORT instead. Short IDs (3000b1c2) work in the instance ID field.
Crosshair stuck on page
Press ESC. If that does not clear it, reload the tab.
Content script test fails
Navigate to a normal http:// or https:// page. Content scripts do not run on about: pages or the new tab page.
Extension lost after restart
Temporary add-ons are removed on Firefox restart by design. Reload from about:debugging. Callto index, manual nodes, and settings all persist in browser.storage.local.
Routing drifts
All dispatch must go through IR.execute() in background.js. No direct fetch-to-Nexus outside the IR layer. No listener-internal routing decisions.

COMPLETE INTEGRATION SNIPPET (copy-paste ready)

JS — works in browser, Node.js, BrainOS, Electron
// Guardian Bridge Client — paste into any project
const BRIDGE = 'http://127.0.0.1:3747';
const CLIENT_ID = 'myapp-' + crypto.randomUUID();

// 1. Handshake
async function bridgeHandshake() {
  const r = await fetch(BRIDGE + '/guardian/handshake', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      instanceId:   CLIENT_ID,
      logicalId:    'myapp',
      capabilities: ['read','write'],
      version:      '1.0.0'
    })
  });
  const d = await r.json();
  console.log('Bridge v' + d.version + ' · token:', d.token?.slice(0,12) + '...');
  return d.token;
}

// 2. Pulse loop
function startPulse(token) {
  return setInterval(async () => {
    await fetch(BRIDGE + '/pulse', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json',
                 'X-Guardian-Token': token },
      body: JSON.stringify({ instanceId: CLIENT_ID, logicalId: 'myapp',
                             status: 'online', ts: Date.now() })
    });
  }, 1500);
}

// 3. Subscribe to events
function subscribeEvents(onEvent) {
  const evs = new EventSource(BRIDGE + '/events');
  evs.onmessage = e => { try { onEvent(JSON.parse(e.data)); } catch(_) {} };
  evs.onerror   = () => { evs.close(); setTimeout(() => subscribeEvents(onEvent), 3000); };
  return evs;
}

// 4. Send a message through Guardian (no API key needed)
async function sendViaGuardian(agentId, text) {
  const r = await fetch(BRIDGE + '/v1/messages', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      provider: 'guardian',
      agentId,                    // chatgpt|claude|deepseek|gemini
      messages: [{ role: 'user', content: text }],
      intent: 'chat'
    })
  });
  if (r.status === 202) {
    console.log('Dispatched — response arrives via /events guardian.link.event');
    // Listen for: { type: 'guardian.link.event', text: '...' }
  } else {
    const d = await r.json();
    throw new Error(d.hint || d.error || 'HTTP ' + r.status);
  }
}

// 5. Bootstrap
(async () => {
  const token = await bridgeHandshake();
  const pulseTimer = startPulse(token);

  subscribeEvents(d => {
    if (d.type === 'guardian.link.event') {
      console.log('AI response:', d.text);
    }
    if (d.type === 'guardian.callto.captured') {
      console.log('New callto:', d.selector, 'on', d.url);
    }
  });

  await sendViaGuardian('chatgpt', 'Hello from my project!');
})();

CAUSAL NEXUS INTEGRATION

Causal Nexus (the causal event engine) connects to the bridge via the adapter module. The bridge SSE stream maps to URCK kernel ingestion:

// In your Causal Nexus adapter
import { createKernel, createAdapter } from 'causal-nexus';

const kernel  = createKernel();
const adapter = createAdapter(kernel);

const evs = new EventSource('http://127.0.0.1:3747/events');
evs.onmessage = e => {
  const d = JSON.parse(e.data);
  // Translate bridge events to URCK ingestion
  if (d.type.startsWith('guardian.callto')) {
    kernel.ingest('guardian:callto:captured', d, 'bridge');
  }
  if (d.type === 'guardian.link.event') {
    kernel.ingest('guardian:response:captured',
      { text: d.text, agentId: d.agentId }, 'bridge');
  }
};
