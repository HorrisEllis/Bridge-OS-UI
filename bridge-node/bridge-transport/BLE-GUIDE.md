# Bridge OS — BLE Transport Guide
## Using Bluetooth Low Energy between Bridge nodes

---

## What BLE gives you

Two Bridge OS nodes that can't reach each other over WiFi or the internet can still communicate over Bluetooth. This matters for:

- **Air-gapped environments** — no network, no problem
- **Close-proximity pairing** — two phones, a phone and a Pi, two laptops at a desk
- **Offline mesh bootstrapping** — BLE to do the initial handshake, then route over WiFi

BLE messages in Bridge OS are chunked into 20-byte ATT MTU packets, reassembled on the other side, and verified with the same Ed25519 signature that every other message uses. Transport changes, trust doesn't.

---

## Step 1 — Install the BLE dependency

Bridge OS uses `@abandonware/noble` for BLE. It's a soft dependency — the node boots without it, BLE just won't be available.

**Linux (Raspberry Pi / Ubuntu):**
```bash
sudo apt-get install -y bluetooth bluez libbluetooth-dev libudev-dev
npm install @abandonware/noble
```

**macOS:**
```bash
npm install @abandonware/noble
# macOS CoreBluetooth works natively — no extra system packages
# You may need to grant terminal Bluetooth permission in System Settings
```

**Windows:**
```bash
npm install @abandonware/noble
# Requires WinUSB driver for your Bluetooth adapter
# Install Zadig: https://zadig.akeo.ie — replace the BT driver with WinUSB
# Then install noble-winrt as well:
npm install noble-winrt
```

**Verify the install:**
```bash
node -e "const n = require('@abandonware/noble'); console.log('noble version:', n.version || 'loaded');"
```

## Step 2 — Enable BLE in Bridge OS

BLE is opt-in via the transport module. In `index.js`, after the node boots:

```javascript
const { createTransportManager, createBLEAdapter } = require('./bridge-transport/index');

boot().then(async (ctx) => {
  const { server, identity, busEmit } = ctx;

  // Create transport manager with BLE enabled
  const transport = createTransportManager({
    identity,
    busEmit,
    getBattery: null,  // optional: supply a battery reader for power throttling
  });

  await transport.start();

  // Listen for messages arriving via BLE
  transport.onMessage((payload, senderUuid, transportType) => {
    console.log(`[BLE] message from ${senderUuid.slice(0,8)} via ${transportType}:`, payload);
    busEmit('transport:message', { payload, senderUuid, transport: transportType }, 'INFO');
  });

  // Wire CFR as normal...
  CFR.install(ctx);
  attachShutdown(server, busEmit, identity.uuid);
});
```

## Step 3 — Sending a message over BLE

BLE requires both nodes to be in range (typically 10–30 metres). One node scans (central), the other advertises (peripheral). Bridge OS uses the **Nordic UART Service** GATT profile — the same profile used by most BLE development boards, so any nRF52/ESP32 running NUS can also connect.

**Send a message to a known peer:**
```javascript
// peerId: the first 8 chars of the peer's UUID (shows in `bridge:boot` log or CFR canvas)
const result = await transport.send('http://192.168.1.5:3747', {
  type:    'mesh:handshake',
  payload: 'hello from node-A',
  uuid:    identity.uuid,
});

if (result.ok) {
  console.log(`Sent via ${result.transport} in ${result.latencyMs}ms`);
} else {
  console.log('All transports failed:', result.tried);
}
```

The transport manager tries adapters in order: BLE → HTTP → cellular. If BLE is unavailable or the peer is out of range, it falls back to HTTP automatically. `result.tried` shows the full attempt list.

## Step 4 — Advertising your node (so other nodes can find you)

Noble handles both scanning and advertising. On Linux, peripheral mode requires the `bleno` package:

```bash
npm install @abandonware/bleno
```

Add to your boot sequence:
```javascript
const bleno = require('@abandonware/bleno');

// Advertise your node UUID as the BLE local name
// Bridge OS peers recognize "BRIDGE:" prefix during scan
const shortId = identity.uuid.slice(0, 8);
bleno.startAdvertising(`BRIDGE:${shortId}`, ['6e400001b5a3f393e0a9e50e24dcca9e'], (err) => {
  if (err) console.error('[BLE] Advertising failed:', err);
  else console.log(`[BLE] Advertising as BRIDGE:${shortId}`);
});

bleno.on('stateChange', state => {
  if (state === 'poweredOn') {
    bleno.startAdvertising(`BRIDGE:${shortId}`, ['6e400001b5a3f393e0a9e50e24dcca9e']);
  }
});
```

## Step 5 — Running on a Raspberry Pi

The Pi is the ideal fixed BLE node — it has built-in Bluetooth and can run 24/7.

```bash
# Give Node.js permission to use BLE without sudo
sudo setcap cap_net_raw+eip $(eval readlink -f `which node`)

# Or run with sudo (less ideal for production)
sudo node index.js

# Verify Bluetooth is up
hciconfig hci0 up
hciconfig -a
```

**Pi systemd unit with BLE permissions:**
The installer generated by `bridge-mobile` includes this automatically. Run:
```bash
node -e "
const { createMobileRuntime } = require('./bridge-mobile/index');
const rt = createMobileRuntime({ identity: require('./data/identity.json') });
const script = rt.generatePiInstaller({ port: 3747 });
require('fs').writeFileSync('./install-pi.sh', script);
console.log('Written: install-pi.sh');
"
sudo bash install-pi.sh
```

The generated unit file includes `AmbientCapabilities=CAP_NET_RAW` so the bridge process can open BLE sockets without root.

## Checking BLE adapter status

From the Bridge OS CLI (`node index.js --cli`):
```
nexus@3747 ❯ module list
```
Look for `bridge-transport` in the list. Then:
```
nexus@3747 ❯ status
```
The status output shows transport adapter availability.

Or via HTTP:
```
GET http://localhost:3747/transport/stats
→ { adapters: [{ type: 'ble', available: true, sent: 0, received: 0 }, ...] }
```

## BLE limits you need to know

| Limit | Value | Why |
|-------|-------|-----|
| Max message size | 512 bytes | ATT MTU limit |
| Default chunk size | 20 bytes | Safe ATT MTU default |
| Typical range | 10–30m | Depends on hardware |
| Connection latency | 15–50ms | After connection established |
| Discovery latency | 1–10s | Depends on advertising interval |
| Concurrent connections | ~7 | BLE spec limit per central |

**For messages larger than 512 bytes:** Use HTTP. BLE in Bridge OS is for peer signalling and mesh bootstrapping — small handshake packets, trust codes, nexus:// URI exchange. For bulk data, use the DHT content store (`bridge-ipfs`) over HTTP.

## Platform notes

**Linux:** Noble requires root OR `CAP_NET_RAW` capability on the node binary. The Pi installer sets this automatically. On desktop Ubuntu, run: `sudo setcap cap_net_raw+eip $(which node)`

**macOS:** Works natively via CoreBluetooth. Bluetooth permission prompt appears on first use. If it doesn't prompt, check System Settings → Privacy → Bluetooth.

**Windows:** The WinUSB driver swap (via Zadig) will break the native Windows Bluetooth stack for other apps while it's installed. Use a dedicated USB BLE dongle if you don't want to affect system Bluetooth.

**iOS/Android:** Full BLE peripheral + central mode via React Native + `react-native-ble-plx`, or via Capacitor. The `bridge-transport` module's BLE adapter runs on the Node.js side only. Mobile integration requires the bridge-mobile runtime with the native BLE bridge injected via `getBattery` and `send` overrides.

## Troubleshooting

**`Error: EPERM: Operation not permitted`** — Missing `CAP_NET_RAW`. Run `sudo setcap cap_net_raw+eip $(which node)` or run with sudo.

**`noble: Adapter not found`** — Bluetooth is off or the adapter isn't recognized. Run `hciconfig hci0 up` on Linux, or check System Preferences on Mac.

**`@abandonware/noble not installed`** — The transport adapter returns `available: false` and falls back to HTTP. Install noble and restart.

**Messages not arriving** — Check that `transport.onMessage()` is registered before `transport.start()`. Also verify both nodes are advertising the `BRIDGE:` prefix — noble filters by this prefix during discovery.

**High latency (> 500ms)** — BLE connection interval may be too long. Noble doesn't expose interval configuration directly; try restarting both nodes closer together.
